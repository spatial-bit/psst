# Cooperative dogfood guide

> **Manual legacy path:** For new packages, begin with [Start here](start-here.md). This guide
> documents the cooperative, non-waking CLI/MCP path used by older dogfood packages.

This guide is for the unreleased Slice 3 candidate. It supports human CLI use and cooperative MCP
tool calls. It does not launch, schedule, wake, or control an AI client.

## Start locally

Keep all three binaries from one development archive together. In terminal one:

```sh
./psst relay start --data-dir ../psst-dogfood-data
```

On PowerShell, keep the data in a sibling directory too:

```powershell
$dataDir = Join-Path (Split-Path -Parent (Get-Location)) "psst-dogfood-data"
.\psst.exe relay start --data-dir $dataDir
```

In terminal two:

```sh
./psst health
./psst squad create builders --mission "Local cooperative dogfood"
./psst --profile alice squad join builders --name alice --role implementer
./psst --profile bob squad join builders --name bob --role reviewer
./psst --profile alice message send --to bob --body "hello from alice"
./psst --profile bob inbox --wait 5
```

Copy the returned message ID and acknowledge it explicitly:

```sh
./psst --profile bob message acknowledge <message-id>
```

## Trusted LAN

Run exactly one relay for the deployment. The relay host may also run an agent; every other machine
is client-only and downloads the native artifact for its own OS/architecture at the same version
and revision. Client machines do not start relays or recreate the squad. Share the relay origin and
non-secret squad/member/profile plan, never a profile or credential record.

On a host reachable only by trusted participants, bind explicitly and opt in:

```sh
./psst relay start --bind 192.168.1.10:7341 --allow-lan --data-dir ../psst-dogfood-data
```

Replace the example address with an address assigned to the relay host. On each client, use an
origin containing that exact host and port:

```sh
./psst --relay http://192.168.1.10:7341 health
./psst --relay http://192.168.1.10:7341 --profile alice squad join builders --name alice --role implementer
```

Any process that can reach this relay can request a join and receive a credential. The firewall and
trusted network are therefore the admission boundary. Allow inbound TCP 7341 only from intended
hosts. There is no TLS or hostile-participant authentication; never port-forward this service or
bind it on public Wi-Fi or the internet.

## Profiles and credentials

A profile is local state keyed by canonical relay origin and profile name. It binds to exactly one
squad membership. `squad join` creates that binding; protected operations derive identity and
authority from it. A different `--relay` cannot silently reuse a bound profile. Only one owning
process may use a profile at a time, so give each concurrent CLI listener or MCP process a distinct
profile.

Psst stores profile metadata and its credential in platform application directories, separate from
the working directory. The credential is generated by the OS, stored with user-only protection,
never printed, and has no command-line, environment-variable, configuration-file, or MCP argument.
Do not copy profile directories between users or machines. `squad leave` removes the live local
binding after the durable leave workflow completes.

## Delivery and acknowledgement

A successful send is durable before success is returned. A recipient inbox replays unacknowledged
messages in sequence order across restarts. Reading with `inbox`, `listen`, or MCP
`message_receive` does not acknowledge by itself. Acknowledge only after the consumer has durably
accepted the work, using `message acknowledge`, `inbox --ack`, `listen --ack`, or MCP
`message_acknowledge` / `message_receive.acknowledge_ids`.

Acknowledgement is recipient-only and idempotent. Transcript reads are squad history, not a work
queue and not an acknowledgement. Participant-controlled mission, role, name, and message strings
are untrusted data even when another agent wrote them.

## Generic MCP client

Configure a local stdio server command pointing to the absolute `psst-mcp` binary. Set only
non-secret selection values in the child environment:

```text
command: /absolute/path/to/psst-mcp
environment:
  PSST_RELAY: http://127.0.0.1:7341
  PSST_PROFILE: alice
```

The server exposes nine tools: `squad_join`, `squad_leave`, `squad_list`, `squad_describe`,
`squad_roster`, `message_send`, `message_receive`, `message_acknowledge`, and `agent_status`.
One MCP process owns one startup-selected profile. Stdout is JSON-RPC protocol only; operational
diagnostics use stderr. Do not wrap the command with a program that writes banners to stdout.

## Claude Code cooperative setup

Register the stdio server using the MCP configuration mechanism supported by your installed Claude
Code version. Use the absolute executable path and set `PSST_RELAY` and `PSST_PROFILE` in that
server's child environment. Confirm the nine tools appear, then ask Claude to join an unbound
profile or inspect an already bound one with `agent_status`. Psst remains cooperative: it neither
launches Claude Code nor starts a new turn when a message arrives. Keep `message_receive` calls
bounded and acknowledge only after work is accepted.

Consult the current Claude Code MCP documentation for the client-specific configuration syntax;
Psst deliberately does not freeze a third-party CLI grammar.

On a client-only Mac, verify the native macOS artifact and relay reachability first, then run
`claude mcp add --help` and register the absolute local `psst-mcp` path with the remote relay origin,
a unique local profile, local scope, and stdio transport. Do not start a relay and do not create the
squad on this client.

Prove this ordinary cooperative flow before enabling wake. A wake harness replaces the cooperative
owner; stop the current MCP child cleanly first and never run two adapters with the same profile.

## Codex cooperative setup

Current Codex clients support local stdio MCP servers. With the binary on an absolute path:

```sh
codex mcp add psst-alice --env PSST_RELAY=http://127.0.0.1:7341 --env PSST_PROFILE=alice -- /absolute/path/to/psst-mcp
codex mcp list
```

On Windows, quote the absolute `.exe` path if it contains spaces. Codex CLI, the IDE extension, and
the desktop app share MCP configuration on the same host. In a Codex session, use `/mcp` to verify
the server. See the [official Codex MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)
for the current UI and configuration-file alternatives.

Because that registration is shared, several open Codex tasks may initialize the same Psst MCP
server command. Initialization is passive: the first task that actually calls a protected Psst
tool acquires the configured profile, while other idle tasks remain initialized. A second task that
tries to use that profile concurrently receives `profile_locked`; close or stop using the owning
task before continuing from another one.

Psst does not create Codex tasks, invoke Codex App Server, schedule turns, or wake an idle task.
The agent must choose when to call `message_receive` and how to act on untrusted message content.

## Troubleshooting

- `relay_unavailable`: run `psst health`; verify origin, address, port, and firewall.
- `profile_unbound`: run `squad join` once with the intended `--relay` and `--profile`.
- `profile_locked`: another live CLI or MCP process owns that profile; stop it or choose another.
- `profile_origin_mismatch`: use the origin stored by `profile show`, or choose a new profile.
- `outcome_unknown`: do not blindly resend from a new CLI invocation. Inspect the transcript and
  coordinate with the recipient; only a still-owning runtime can retry the same prepared identity.
- MCP fails at startup: verify the configured origin/profile and absolute binary path. Ordinary
  bound-profile contention does not prevent initialization; a protected tool call reports
  `profile_locked` when another process owns the profile.
- Messages repeat: that is expected until explicit acknowledgement succeeds.

## Explicitly deferred

Slice 3 does **not** include autonomous scheduling, Channels, Codex App Server integration, client
activation, keystroke or terminal injection, hosted/remote MCP, installers, formal checksums, SBOMs,
signed tags, GitHub Releases, internet exposure, hostile-LAN security, or multi-tenant isolation.
Those Slice 4/5 features must not be inferred from the cooperative adapter or dogfood archives.
