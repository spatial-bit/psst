# ADR 0005: Slice 4 harnessed activation boundary

Status: accepted

## Context

Slice 3 proved that independently running Claude Code and Codex sessions can cooperate through one durable Psst relay. Slice 4 must activate an idle supported client when durable mail is pending without turning participant-controlled message text into host control input, losing a wake during a process boundary, or starting duplicate turns for a burst of messages.

Claude Code Channels and Codex App Server expose different host protocols. Claude Channels are a research-preview MCP extension enabled per session; Codex App Server is a versioned local JSONL protocol with generated schemas. The relay must remain unaware of both.

## Decision

- A client-neutral activation engine in `psst-application` owns observation, coalescing, reconciliation, retry/backoff, turn occupancy, cancellation, and sanitized diagnostics.
- Relay truth remains the durable inbox. Wake records are local hints and never replace inbox retrieval or acknowledgement.
- The engine has at most one outstanding activation for a profile. A burst while quiet becomes one wake; mail arriving while waking or running sets a reconcile-needed bit rather than preempting the active turn.
- A wake contains only fixed Psst instructions plus trusted metadata derived by the adapter: profile, squad, pending count, highest priority, and oldest message ID. It never contains message bodies, credentials, sender-controlled names, correlation values, or reply text.
- Empty polls never invoke a host. Retrieval remains explicit and never acknowledges. After a host turn completes, the engine re-reads pending mail and schedules another bounded activation only when unacknowledged mail remains.
- Reconciliation runs at startup, after every activation outcome, and at least every 60 seconds. It recovers a dropped notification or adapter restart from relay truth.
- Retryable host failures use capped exponential backoff with jitter. Permanent incompatibility becomes visible `blocked` state; retry loops, queues, retained diagnostics, and shutdown are bounded.
- Claude harnessed mode extends the existing `psst-mcp` stdio server with the experimental `claude/channel` capability and emits `notifications/claude/channel`. It is one-way in version one: Psst does not relay permissions and never launches Claude with `claude -p`. Custom-channel preview flags and allowlist limitations remain explicit operator opt-ins.
- Codex harnessed mode is a separate `psst-codex` process. It launches or connects to local `codex app-server`, performs `initialize`/`initialized`, consumes schemas generated by the installed Codex version, resumes one configured thread (or creates one under an explicit policy), and uses `turn/start`. Ordinary mail never calls `turn/interrupt` or `turn/steer`.
- Host adapters report accepted, running, completed, retryable failure, permanent failure, and shutdown outcomes through a narrow trait. They do not own inbox acknowledgement or credential persistence.
- No PTY, terminal keystroke injection, public listener, permission relay, or remote host control is included. Any later PTY fallback requires a new decision and explicit opt-in.

## Consequences

The first vertical slice is the deterministic activation engine and fake host, followed by Claude and Codex protocol adapters, then packaging and live dogfood. Fake-host tests prove state-machine safety; opt-in real-client tests prove current host compatibility. Because both external surfaces can change, installed-version capability/schema checks fail closed and diagnostics name the unsupported boundary without exposing secrets.
